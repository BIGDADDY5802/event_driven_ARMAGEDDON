# Lab 12B Runbook — Executive Report Generator

## Purpose

Reads the three SEIR pipeline ledgers (`waf-events`, `waf-correlation-findings`,
`security-incidents`), builds a synchronized executive PDF + JSON report pair,
uploads both to S3. Informational only — performs no containment.

Lives in the same consolidated Terraform state as Labs 11A/11B/12A
(`lab12/dev12b/terraform` locally). Extends the pipeline; does not touch its
existing resources.

---

## Architecture

```
waf-events ─┐
waf-correlation-findings ─┼─► executive-report-generator (Lambda) ─► Bedrock (narrative)
security-incidents ─┘                     │
                                            ▼
                              event-driven-arm-bucket/executive-reports/
                                    YYYY/MM/DD/pdf/*.pdf
                                    YYYY/MM/DD/json/*.json
```

| Resource | Name | Notes |
|---|---|---|
| S3 bucket | `event-driven-arm-bucket` | Created for this lab. `force_destroy = true`, public access blocked, SSE-S3 (AES256) |
| Lambda | `executive-report-generator` | Python 3.12, 1024 MB, 120s timeout, 512 MB ephemeral (default) |
| IAM role | `report-executive-role` | Least-privilege, scoped ARNs, no `Resource: "*"` except the two AWS actions that structurally require it |
| Log group | `/aws/lambda/executive-report-generator` | `var.log_retention_days` |
| Bedrock model | `us.anthropic.claude-haiku-4-5-20251001-v1:0` | CRIS two-grant pattern — matches the other 3 Bedrock-calling Lambdas in this stack, not the spec's literal `claude-3-haiku-20240307` default |

### IAM permissions (all scoped, not account-wide)

- `dynamodb:Scan` on the 3 table ARNs
- `bedrock:InvokeModel` — CRIS profile ARN (account+region scoped) + foundation-model ARN (region wildcard, structurally required for cross-Region inference)
- `aws-marketplace:Subscribe` / `Unsubscribe` / `ViewSubscriptions` — `Resource: "*"` required, these 3 actions don't support ARN scoping at all
- `s3:PutObject` scoped to `event-driven-arm-bucket/executive-reports/*` only
- `logs:CreateLogStream` / `PutLogEvents` scoped to this Lambda's own log group

## Verification (do this every time, don't assume a clean apply means it works)

1. **Confirm packaging actually happened** — before invoking, check the build
   directory isn't just the handler file alone:
   ```bash
   ls -la ./build/report_executive_pkg
   ```
   Expect `lambda_function.py` *and* `reportlab/`, `PIL/`, `charset_normalizer/`
   directories. If it's only the `.py` file, the `null_resource` pip install
   silently did nothing — see Gotcha #1 below.

2. **Invoke manually**:
   ```bash
   aws lambda invoke \
     --function-name executive-report-generator \
     --cli-binary-format raw-in-base64-out \
     --payload '{"report_period_hours": 24}' \
     ./report_invoke_response.json
   cat ./report_invoke_response.json
   ```
   Expect `"StatusCode": 200` with **no** `"FunctionError"` key. If
   `FunctionError: "Unhandled"` appears, the invoke API call itself succeeded
   but the Lambda code crashed — read the `errorMessage` in the body, don't
   just look at `StatusCode`.

3. **Confirm the artifacts actually landed**:
   ```bash
   aws s3 ls s3://event-driven-arm-bucket/executive-reports/ --recursive
   ```

4. **Pull a report down and read it** — a `200` and a nonzero file size prove
   the pipeline ran, not that the content is correct. Open the PDF.

## Gotchas hit during this build (both passed a clean `terraform apply` — evidence caught them, not the plan)

### Gotcha #1: Empty `requirements.txt`

**Symptom:** `terraform apply` succeeds with 0 errors. Lambda invoke returns
`FunctionError: "Unhandled"`, `errorMessage: "No module named 'reportlab'"`.

**Root cause:** `requirements.txt` was 0 bytes. `pip install -r requirements.txt`
against an empty file installs nothing and exits `0` — no error, no warning,
nothing in the `null_resource`'s `--quiet` output to catch it.

**Check:**
```bash
cat ../lambda/report_executive/requirements.txt
```
Should show `reportlab==4.4.3`. If empty, that's the bug.

**Fix:** rewrite the file with real content, then force the packaging step to
rerun (the `null_resource`'s `triggers` hash file *content*, so a content
change alone should trigger it automatically on next `plan`):
```bash
echo "reportlab==4.4.3" > ../lambda/report_executive/requirements.txt
terraform plan -out=tfplan
terraform apply tfplan
```

### Gotcha #2: Windows-compiled transitive dependency (the harder one)

**Symptom:** After fixing Gotcha #1, `requirements.txt` has the right content,
`pip install` reports success, files land in the build directory — but the
Lambda would still crash on import at runtime if deployed as-is.

**Root cause:** `reportlab==4.4.3` itself is a pure-Python wheel (verified
against PyPI — no platform-specific build). But it pulls in `pillow>=9.0.0` as
an **unpinned transitive dependency**, and Pillow ships compiled C extensions.
A plain `pip install` on Windows/Git Bash grabs Windows binaries
(`pillow-*-win_amd64.whl`, `.pyd` files) — those don't run on Lambda's Linux
runtime. `charset-normalizer` (pulled in by reportlab too) has the same
problem via its `mypyc`-compiled build.

**This is the one lesson worth internalizing:** checking that a package's own
PyPI wheel is pure-Python is *not* sufficient — its dependency tree needs the
same check. A single `py3-none-any` wheel can still drag in compiled,
platform-locked dependencies you never explicitly asked for.

**Check:**
```bash
find ./build/report_executive_pkg -name "*.pyd"
```
Any hits here mean Windows binaries are in the deployment package —
guaranteed Lambda crash on import.

**Fix:** force `pip` to fetch Linux-target (`manylinux`) wheels instead of
matching the local machine. This is already baked into the `null_resource`'s
`command` block in `report_executive_lambda.tf`:
```bash
pip install \
  -r requirements.txt \
  -t <build_dir> \
  --platform manylinux_2_28_x86_64 \
  --platform manylinux2014_x86_64 \
  --implementation cp \
  --python-version 3.12 \
  --abi cp312 \
  --only-binary=:all: \
  --upgrade
```
Note both `--platform` flags are needed — Pillow 12.3.0 only publishes
`manylinux_2_27`/`manylinux_2_28` tags (not the older `manylinux2014` tag that
`charset-normalizer` uses), so a single `--platform` value doesn't cover both
dependencies. Verified via PyPI's JSON API before trusting this, not assumed.

**Re-verify after any dependency change:**
```bash
find ./build/report_executive_pkg -name "*.pyd"   # expect: nothing
find ./build/report_executive_pkg -name "*.so"     # expect: files tagged
                                                     # cpython-312-x86_64-linux-gnu
```

## Known non-blocking issue (tracked, not fixed)

Bedrock's generated narrative has shown a **self-contradiction between
sections** on at least one real report: "Material Changes" stated the source
IP was "(US-based)" using the real `top_countries` evidence field, while
"Limitations and Unknowns" on the *same report* claimed geolocation data
"is not available." The evidence pipeline is correct (the country field is
real, sourced from AWS WAF's own geo-IP lookup, not invented) — this is
Bedrock failing to stay internally consistent across sections of its own
output. The system prompt requires evidence-grounding and honesty about
missing baselines, but doesn't explicitly require cross-section consistency.

**Status:** watching for recurrence. Revisit the Bedrock prompt (add an
explicit consistency requirement) if this shows up again on a future report
with real findings, rather than fixing preemptively on one instance.

## Related pipeline components (read-only dependencies, not owned by 12B)

| Table | Written by | Schema fields this Lambda reads |
|---|---|---|
| `waf-events` | `waf_bedrock_analyzer.py` (5-min schedule) | `event_epoch`, `source_ip`, `uri`, `rule`, `action`, `country` |
| `waf-correlation-findings` | `handler.py` correlation agent (15-min schedule, `MINIMUM_EVENT_COUNT=3`) | `severity`, `risk_score`, `primary_source_ip`, `primary_target`, `status`, `created_at`, `window_end` |
| `security-incidents` | `soar_response_agent.py` (EventBridge-triggered, near-real-time) | `incident_id`, `severity`, `status`, `playbook`, `human_review_required`, `created_at` |

If a future schema change touches any of these field names in the upstream
Lambdas, this report generator's metrics functions
(`calculate_waf_metrics`, `calculate_finding_metrics`,
`calculate_incident_metrics`) will silently return zeros/defaults for the
renamed field rather than erroring — `dict.get()` with defaults everywhere,
by design, but it means a schema drift here fails silently, not loudly.
