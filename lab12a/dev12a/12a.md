## 3. Lab 12A — SEIR pipeline architecture

```
AWS WAF (chewbacca-11a-intake-acl)
   │  logs to
   ▼
CloudWatch Logs (aws-waf-logs-chewbacca-11a-intake)
   │  pulled every 5 min by
   ▼
waf-bedrock-analyzer (Lambda)
   │  normalizes + writes, atomic on request_id
   ▼
DynamoDB: waf-events
   │  scanned every 15 min by
   ▼
waf-correlation-agent (Lambda)
   │  deterministic scoring + Bedrock narrative
   ▼
DynamoDB: waf-correlation-findings
   │  publishes "WAF Threat Finding Created" event
   ▼
EventBridge bus: seir-security-bus
   │  routed by severity (3 rules: LOW / MEDIUM-HIGH / CRITICAL)
   ▼
soar-response-agent (Lambda)
   ├─→ DynamoDB: security-incidents (creates incident record)
   ├─→ SNS: soar-incident-notifications (analyst notification)
   └─→ (CRITICAL only) SNS: soar-critical-alerts, published directly
        by EventBridge in parallel with the Lambda, not via the Lambda
```

### 3.1 Why the analyzer isn't push-based

Originally built as a CloudWatch Logs subscription filter (push, real-time). **Replaced entirely** after the actual Lab 12 spec (instructor-provided, authoritative) required a pull-based design: `LOOKBACK_MINUTES`/`MAX_LOG_EVENTS`-driven `FilterLogEvents` calls on a schedule, with a Bedrock call **per individual event** (not per correlation batch), output written to CloudWatch via the analyzer's own log lines.

### 3.2 Idempotency, two different mechanisms

- **`waf-events` table**: hash key is `request_id` (WAF's own unique-per-request identifier), **not** a random UUID. This is what makes the pull-based analyzer's overlapping `LOOKBACK_MINUTES` windows safe — a conditional `put_item` on `attribute_not_exists(request_id)` guarantees a re-read event is skipped, including skipping the per-event Bedrock call, not just the duplicate row.
- **Correlation Agent + SOAR**: both use a "claim first" pattern — `claim_run()` / `claim_finding()` — an atomic conditional write keyed on the EventBridge event's own `id`, executed *before* any expensive work (Bedrock, SNS), so a Lambda retry of the same delivery can't double-process.

**Known gap, tracked, not fixed:** the WAF Bedrock Analyzer itself has no protection against CloudWatch Logs' at-least-once *delivery* semantics beyond the `request_id` key already covering it — this is actually fully covered, superseding an earlier tracked gap (`GAP-SEIR-1`) that applied to the now-retired push-based analyzer.

### 3.3 Bedrock model — three real failures, in order, before it worked

1. `anthropic.claude-3-haiku-20240307-v1:0` → `ResourceNotFoundException`, model retired to Legacy status on Bedrock.
2. Switched to `anthropic.claude-haiku-4-5-20251001-v1:0` → `ValidationException`, this model doesn't support on-demand direct invocation, requires a cross-Region inference profile.
3. Switched to `us.anthropic.claude-haiku-4-5-20251001-v1:0` (CRIS profile ID) → `AccessDeniedException`, missing AWS Marketplace subscription permissions (`aws-marketplace:Subscribe`, `Unsubscribe`, `ViewSubscriptions` — these three actions don't support resource-level ARN scoping, `Resource: "*"` is the only valid option per AWS's own IAM docs).

**Final working IAM shape**, applied to all three Lambdas that call Bedrock (analyzer, correlation agent, SOAR):
- `bedrock:InvokeModel` on the specific inference-profile ARN (account+region scoped)
- `bedrock:InvokeModel` on the underlying foundation-model ARN (region wildcard — structurally required by how cross-Region inference routes, not a shortcut; model ID itself stays pinned)
- `aws-marketplace:{Subscribe,Unsubscribe,ViewSubscriptions}` with `Resource: "*"` (AWS-mandated, no narrower option exists for these three actions)

### 3.4 A real runtime bug, not caught by any static check

`active_span_minutes = round(seconds / 60, 2)` in the Correlation Agent produces a native Python `float`. boto3's DynamoDB Table resource rejects native floats outright — `TypeError: Float types are not supported. Use Decimal types instead.` Fixed with a `native_to_decimal()` write-side helper (mirroring the existing `decimal_to_native()` reader) applied immediately before `put_item`. Not caught by `py_compile`, `terraform validate`, or `terraform plan` — only surfaced on the first real invocation against real data.

### 3.5 EventBridge severity routing

Original design doc specified only two rules (Medium/High, Critical). **Deliberately added a third (Low)** so SOAR's `RECORD_ONLY` playbook — defined in `soar_response_agent.py`'s own `PLAYBOOKS` table — is actually reachable by the automated pipeline instead of only by manual test invokes.

| Rule | Severity | Targets |
|------|----------|---------|
| `soar-low-severity-findings` | LOW | `soar-response-agent` |
| `soar-medium-high-severity-findings` | MEDIUM, HIGH | `soar-response-agent` |
| `soar-critical-severity-findings` | CRITICAL | `soar-response-agent` **and** `soar-critical-alerts` SNS topic directly (EventBridge fan-out, deliberate redundancy — an alert reaches someone even if the Lambda is broken/throttled) |

## 4. End-to-end verification (real data, not synthetic)

Test traffic: 5–9 `curl POST` requests to `/prod/intake` from a single source IP, generating consistent `MEDIUM` severity findings (risk score 30 — driven by event-volume thresholds, not malicious indicators).

**Full chain confirmed, final run:**
1. `waf-bedrock-analyzer` — 5 events read, 5 written (unique `request_id`s), 5 Bedrock summaries generated and logged. Re-invoked immediately after: 0 written, 5 skipped as duplicates, 0 Bedrock calls — **idempotency proven, not just implemented**.
2. `waf-correlation-agent` — 5 events correlated, `MEDIUM`/30, real Bedrock narrative generated, finding saved, **event published to `seir-security-bus`** (`Published finding-created event for <finding_id>` in logs).
3. `soar-response-agent` — invoked **automatically by EventBridge**, zero manual invoke in this hop. Claimed the finding, selected `NOTIFY_ANALYST` playbook, generated a Bedrock incident summary, created `security-incidents` record, published SNS notification, marked finding `RESPONSE_COMPLETED`.

**Notable validation of the architecture itself:** the Correlation Agent's Bedrock narrative text opined *"Overall Severity: LOW"* in its prose, while the pinned deterministic `severity` field (used for every actual decision — playbook selection, EventBridge routing) stayed `MEDIUM` throughout. Bedrock's free-text opinion was correctly **never consulted for the decision** — only for narration. Confirms the "Bedrock explains, never decides" design principle holds under a real disagreement between the LLM and the deterministic scorer, not just in theory.

## 6. Known gaps / deliberately deferred

- **CRITICAL path unverified with real data** — requires deliberately contrived traffic (multiple rule types, sensitive URI, high event count) to actually hit the risk-score threshold. Not yet tested.
- **`MAX_LOG_EVENTS=500` scaling limit** — the analyzer processes events sequentially with a Bedrock call each; 500 sequential calls could approach or exceed the Lambda's 300s timeout under real load. Fine for lab-scale traffic; would need fan-out (SQS + concurrent invocations, or Step Functions) for production volume.
- **15-min correlation cadence vs. 60-min window** — deliberate choice (faster feedback for testing) that means the same underlying events get re-correlated into up to 4 separate findings per hour. Acceptable for testing; worth tuning before any real use.
- **Filename hygiene** — a few files exist under slightly different names than originally given (`seir_dynamo_db_...` vs `seir_dynamodb_...`, `..._scheduler.tf` vs `..._schedule.tf`). Functionally fine (no duplicate-resource conflicts confirmed), but worth a final pass to reconcile names for clarity.
